# reLayout — Architecture & Build Reference

Deep reference. For day-one orientation read [`CLAUDE.md`](../CLAUDE.md) first; this is the detail it links to.

## Build env vars (read by `scripts/build.sh`)

- `RELAYOUT_VERSION` — override version string.
- `RELAYOUT_RELEASE=1` / `RELAYOUT_DEV=1` — force release vs dev bundle id/name.
- `WITH_SPARKLE=1` — fetch & embed Sparkle 2.6.4 framework, compile with `-D SPARKLE`. CI uses this for releases.
- `RELAYOUT_DEBUG=1` — compile with `-D DEBUG`: `dbg()` traces to `/tmp/relayout.log` (`scripts/run.sh` sets it).
- `SIGN_IDENTITY` — Developer ID Application identity. Triggers Hardened Runtime + secure timestamp (notarization-ready). Without it, uses `ReLayout Self Signed` if present, else ad-hoc.

Owner identity — **no owner values are hardcoded in the repo.** Resolution order in `build.sh`: `RELAYOUT_*` env vars (CI sets them from repository *variables*) → `scripts/identity.env` (gitignored local file; copy `identity.env.example`) → neutral fallbacks (`com.example.relayout`, repo slug derived from the git origin remote, Sparkle disabled). Release builds (`RELAYOUT_RELEASE=1` / exact tag) **fail** under the neutral id. See [`RELEASING.md`](RELEASING.md) → "Forking".

- `RELAYOUT_BUNDLE_ID` — base bundle id (dev builds append `.dev`).
- `RELAYOUT_DISPLAY_NAME` — app display name (dev appends ` (dev)`).
- `RELAYOUT_REPO_SLUG` — GitHub `owner/repo` for the About link (injected into the bundle as `RLRepoSlug`; empty hides the link) and the Homebrew cask.
- `RELAYOUT_FEED_URL` — Sparkle `SUFeedURL`. Empty → Sparkle keys removed from the bundle, automatic checks disabled.
- `RELAYOUT_SU_PUBLIC_KEY` — Sparkle `SUPublicEDKey`; **pairs with the `SPARKLE_ED_PRIVATE_KEY` secret** — replace both together.
- `RELAYOUT_TAP_REPO` — Homebrew tap `owner/name` (read by `packaging/homebrew/update-cask.sh`, not build.sh).

## Release flow

Tag `vX.Y.Z` → `.github/workflows/build.yml` signs (Developer ID), notarizes (`notarize.sh`, App Store Connect API key), staples, publishes a GitHub Release with `reLayout.dmg` + `reLayout.zip`, updates the Sparkle appcast + Homebrew cask. See [`RELEASING.md`](RELEASING.md) for the secret list.

Dev vs release builds use **different bundle IDs** (the base `RELAYOUT_BUNDLE_ID` vs the same id + `.dev`) and different `.app` names so macOS keeps separate Accessibility grants and UserDefaults.

## Conversion engine (`Core/Engine.swift`)

Platform-free Swift. **No** AppKit/Carbon/WinSDK imports. Shared verbatim by:
- macOS app — compiled together with `macos/main.swift` by `scripts/build.sh`.
- Windows port — imported as the `ReLayoutCore` SwiftPM module (`Package.swift`).
- Tests — both `scripts/run-tests.sh` (links into the macOS binary with `-DTESTING`) and `swift test` (uses `Tests/ReLayoutCoreTests`).

The core algorithm is **not** a character→character table. It is:

```
char --(source layout reverse)--> KeyStroke (physical key + mods)
     --(target layout)         --> char
```

Each platform builds a `LayoutMaps` (`charToStroke`, `strokeToChar`, `isCyrillic`) over the actually-installed layouts:
- macOS: Carbon `UCKeyTranslate`.
- Windows: `ToUnicodeEx`.

This is why the Option/AltGr layer (`ß`/`æ` ↔ `ы`/`э`) works automatically — both produce the same `keyCode + Option`, so the reverse-then-forward lookup converts them without hand-coded tables.

`transliterate(_:from:to:)` is the entry point. Word-level "is this the wrong layout?" detection uses script heuristics (`hasCyr`, `isLatinLetter`) — only words in the script of the **currently active** layout are converted; the rest of the selection is preserved. `dominantScript` / `textHasScript` / `wordTokens` back a hybrid fallback: when the active layout no longer matches what was typed (user switched after mistyping), the source is inferred from the text's majority script instead of the system layout.

The hotkey acts on a selection — what the user pointed at. With nothing selected it converts `AutoRun.hotkeyTarget`: the word being typed before the caret, or the last word followed only by spaces (erased with those spaces and retyped with them). The key monitor feeds the run on both platforms whether or not auto-correct is on. The target ends at any other key after the spaces (which starts the next word), at Tab/Return, at any conversion (auto fix, hotkey, undo), and at every caret-moving event (click, Cmd/Ctrl shortcut, navigation, focus change); backspacing all the spaces makes the word the one being typed again. No target means nothing to convert. Other unselected text is never guessed at: no line grab, no word-at-the-caret window. `caretWord(_:)` stays in the engine for the auto mode.

A word that mixes scripts comes from a **mid-word layout switch** ("ghjсто"). `convertWrong` converts only such a token's src-script runs (`convertScriptRuns`), and `planRetype` sends a single-word selection to `fixMixedWord` first: which half is wrong is not decidable from the layouts ("ghjсто" wants its head fixed, "мирqwerty" its tail), so both readings are trigram-scored and the better wins — no confidence gates, the hotkey is an explicit request.

`Core/Auto.swift` — the auto-correct mode's platform-free half, shared by both apps: `decideAutoTarget` (the trigram decision), `AutoRun` (the typed-word run — word, punctuation trail, previous word — with its feed/Backspace/short-word rules) `awaitSettledField` (the Enter follow-up's settle loop), and the hotkey's `planRetype` / `bestConversion` / `pickTarget` / `fixMixedWord` (which layouts a selection converts between: with several enabled layouts of the other script, the one whose language model reads the conversion best — only installed layouts' models are consulted; the positional `pickTarget` rule when models are missing). Each app only feeds it keystrokes and performs the fix it returns.

`Core/Strings.swift` — `parseStrings`, a reader for the `.strings` files, so the Windows port shows the macOS translations (macOS itself reads them through `Bundle`).

`Core/Trigram.swift` — a character-trigram language model used by the auto-correct mode. `TrigramModel.score(_:)` returns a word's length-normalized mean trigram log-prob under a per-language model; models are generated offline (`scripts/trigram/gen.py`) from FrequencyWords 50k lists and shipped as `Resources/trigram/<lang>.txt`. The uk list is first passed through `scripts/trigram/filter.py` with dict_uk's word forms: raw, it is a quarter Russian by mass, which taught the model to accept Russian words. Platform-free, so it lives in the engine.

## macOS app (`macos/main.swift`, single file)

Holds everything outside the engine:
- `Loc` / `L(_:)` — localization. UI strings live in `Resources/<lang>.lproj/Localizable.strings`. Languages are discovered from shipped `.lproj` bundles; user override in `UserDefaults["language"]` switches live, no relaunch.
- Hotkey system — supports **combos** (e.g. ⌃⌥R via `RegisterEventHotKey`) and **modifier taps/chords** (e.g. tap left Option). Tap/chord detection uses a `CGEventTap` and fires only on release with no other key/mouse press in between; a `tapPolluted` guard ignores cycles where an out-of-set modifier appeared. A hotkey can also be a **tap sequence** (`Hotkey.taps` — N activations within `doubleTapWindow`, e.g. double-tap Shift), recorded by repeating it in the `ShortcutField`. A hotkey is a `Hotkey` value (mode, code/mods or chord, taps, display; `load`/`save` under a UserDefaults prefix). Two slots (`HotkeySlot`): `.retype` (keys `hk*`, default tap left Option) and `.autoToggle` (keys `autoHk*`, unset by default — nothing registered), the Carbon `EventHotKeyID.id` telling them apart; both modifier-tap hotkeys share the one `CGEventTap`, each with its own `TapCycle`. A hotkey whose activation equals the other's (`clashes`: same combo, or same chord whatever the tap count) is refused with the conflict line. The toggle flips `autoMode` like the checkbox and does nothing while auto-correct is unavailable (one script; the checkbox is disabled then). The auto tap lets either combo hotkey's keyDown (`isCombo`) pass untouched: no run reset, no feed.
- Auto-correct mode (`autoMode`, default off; Settings checkbox or the optional toggle hotkey; while on and available, `updateStatusIcon` draws a dot in the template icon's top-right corner — a template keeps only alpha, so it is the bar's foreground at 60 % alpha, not green) — a second `CGEventTap` (keyDown) feeds the engine's `AutoRun` and, on a word boundary, runs `autoDecide` (engine `decideAutoTarget`: trigram scores; a word is junk for a cross-script conversion only if no enabled layout of its script, nor the languages typed on any layout of that script (ru + uk for Cyrillic, en for Latin, enabled or not), reads it — Russian typed on the Ukrainian layout ("еще") is not a wrong-layout word, though its Latin reading "tot" is English, nor Ukrainian on a Russian one ("лише" → "kbit"), nor English on a Polish one ("but" → "иге"); targets are the layouts of the other script plus, with the experimental `autoSameScript` setting (`sameScript:` parameter, default off; its checkbox is enabled only when `hasSimilarLayouts` finds two enabled layouts of one script and different languages with models), same-script layouts of another language — ru ↔ uk under `autoSameScriptMargins`, 1.5 into uk and 1.0 into ru, since the Russian model underrates "ы" words while the dictionary-cleaned uk model is strict, and the pairs differ in four letters) → `autoCorrect` deletes + retypes the fixed word and switches layout. Short words (1-2 chars, e.g. prepositions `d`→в, `yf`→на) score fine — the model pads `^^w$` — but aren't trusted alone; `AutoRun.plan` remembers a short candidate and only converts it when it borders a real conversion of the same script, so a following long word swallows a pending preposition into one edit ("d ljhjut"→"в дороге"), two short candidates in a row agree and are fixed together ("пщ ещ"→"go to"), a short word with no candidate between chain words rides along with the chain ("ot" in "nf ot [fktgf"→"та ще халепа", `AutoRun.bridge`), while a lone short junk token is left untouched. A 3-letter word whose two readings both score at least `autoAmbiguous` (−3.0) is two real words on the same keys ("рук" / "her"): `decideAutoTarget` flags it `ambiguous` and `AutoRun.plan` treats it like a short word — fixed only next to a neighbour, never by the Enter follow-up. Learned words (engine `LearnedVerdict`, `learnedKey`, `hotkeyMisses`; `UserDefaults` `autoLearned` / `autoKept`): with auto mode on, every hotkey conversion asks the engine which of its words auto mode would have left alone (`hotkeyMisses`: in a phrase every word of 3+ letters, for a single word only one auto would leave or a short one; vetted by the destination model, only results that read, `autoLearnPlausible`) and counts them (`autoLearnCounts` / `AutoCorrectLearnCounts`); the third correction of the same typed form promotes it to `convert` (`autoLearnRepeats`), the undo takes one count or the verdict back; undoing an auto-correction stores its words as `keep` at once. Learning by revert (engine `RevertWatch`, both platforms): within 15 s of an auto-correction, an edit that may delete text (Backspace, Delete, arrows, a click, a Cmd/Ctrl shortcut) followed by the same typed word again marks it `keep` and leaves it — however the correction was erased (letter by letter, a selection, or typing over one). `decideAutoTarget` consults the verdict first — `keep` returns nil, `convert` skips the garbage, margin and punctuation gates but not the short-word rule. No language dictionary: only strings this user has fixed. The one dictionary used is the system's, behind the experimental `autoSpell` setting (default off; its checkbox is enabled only when `NSSpellChecker.availableLanguages` covers an enabled layout's language; a sub-option ruled out by the system shows off, one disabled only because auto-correct is off shows its stored state; the preference is kept): `autoDecide` passes the trigram decision through engine `spellCheckedTarget` (drop a cross-script conversion of a spelled-right word into a misspelled one; convert a 4+-letter pure-letter word the trigrams leave alone when it scores below `autoGarbage`, no dictionary of its script has it and one of the other script has its conversion). Then engine `spellRepairedTarget` repairs one typo inside a wrong-layout word (typed word: 4+ pure letters, not capitalized, junk to its model, misspelled in its script): when the conversion is misspelled, `repairedSpelling` tries one doubled letter removed or two adjacent letters swapped, else the system's `guesses` one edit away (`isOneEdit`); exactly one dictionary word wins, otherwise the plain decision stands (converted with the typo, or left). A repair itself is never learned as a conversion; undoing or reverting it stores the typed word as `keep` like any auto-correction (the word did not want converting at all). The hotkey never repairs typos. The check is a synchronous `checkSpelling` on the tap's thread (median 0.5 ms, 1 % at 50–100 ms; marked `shortcut:`). Windows does the same through the Windows Spell Checking API (see the Windows port). Settings shows the count with View… (sheet, remove rows) and Reset (confirmed). Punctuation that is a letter on an enabled Cyrillic layout (`,`=б, `'`=э, `;`=ж, `[`=х …) buffers as word material, so ",skj" fixes to "было"; `autoWordCore` (engine) vets the shape — a trailing mapped char is word material too ("vj]" → "мої", "gj[j;" → "похож") — the word minus its edge punctuation must not already be plausible ("hello," stays), and a word shorter than 3 chars without its trailing mapped run waits for a neighbour like a preposition ("vs." would read as "мію") — and the converted form must clear an absolute plausibility gate on top of the usual margin (`autoPunctPlausible` −3.6 for punctuation-bearing words, `autoPlausible` −4.0 for pure-letter ones, so junk never converts into lesser junk). Other punctuation/symbols right after a word (not word material on any enabled layout) collect in the run's trail; the word is still judged only at whitespace, and the trail is retyped through the same layouts, so "ltkfq? " fixes to "делай, " — no character table, and "@"/"/" inside an address or path (never followed by whitespace) end nothing. The character a keystroke contributes comes from the *current layout's* maps (`layoutChar`: key code + modifiers → `strokeToChar`), not from the event's own string, which is attached upstream of the window server and still carries the previous layout's letters right after a conversion switches it; the event's string remains the fallback for keys no layout maps. A keystroke producing no character (Globe/fn, dead keys, F-keys) is skipped instead of ending the word run — otherwise the layout switch itself would drop the pre-switch half. Switching the layout mid-word leaves one word with both scripts ("ghjсто"): `autoDecide` takes a mixed-word branch built on engine `convertScriptRuns` (converts only the runs of the source layout's script), trying both readings — fix the pre-switch run into the current script ("просто", no input-source switch) or the current-layout run into the cross-script candidate — each scored under the model of its resulting script. A user deny-list (`autoExcludedApps`, edited via the Exceptions sheet) plus a secure-text-field check gate it per app; our own synthesized events carry `synthMarker` so the monitor ignores them. Fast typists outrun the retype — the delete+retype of a finished word would interleave with whatever was typed since, mixing the text and converting the wrong characters — so the auto tap is a `.defaultTap` and, while a correction is in flight (`autoPending`), it *swallows* text-producing keys into `autoHeld` and returns nil; `finishCorrection` replays them once the queue drains, feeding each key through the word buffer *before* typing it — a replayed boundary that starts another correction is typed by that correction, and the keys after it go back on hold. Return is never swallowed and never corrects before it lands (it may submit a launcher query or a chat message). `autoEnterFollowUp` reads the focused field over AX (`fieldSnapshot`: length, caret, 64 chars before it) and, under the keystroke gate, `finishEnter` polls until the field is stable for ~75 ms (the system capitalizes the word ~50 ms after the break), then engine `enterOutcome` decides: only `.newline` deletes break + word and retypes the fix + a real Return. Short words, held Returns, views whose `AXValue` is not settable (Terminal, Ghostty: Return there runs the line), fields without `AXStringForRange` (Chromium/Electron) and the Settings sub-option `autoEnterNewline` (default on, disabled while auto-correct is off) keep plain Return. Replayed Return and a swallowed Tab boundary are posted as real keys with their Shift/Option flags (`typeKey`), never as a Unicode "\r"/"\t": apps act on the key code. The tap also watches mouse-downs: a click, like any Cmd/Ctrl shortcut, may move the caret or focus, so either ends the run (buffer, trail and pending preposition) — otherwise a later correction deletes text before the new caret and pastes the stale word there. Only character keys are held: modifiers, Globe, arrows and delete always pass through, so a stuck correction can never freeze the keyboard.
- Selection read/write — Accessibility API first (so DeepL etc. don't see clipboard churn); clipboard fallback reads the selection with **Cmd+C** (copy keeps the selection and typing replaces exactly it — smart cut-and-paste in Word-like apps would otherwise swallow an adjacent space along with a cut word). Saves/restores pasteboard. VS Code copies the whole caret line when nothing is selected; its clipboard metadata (`isFromEmptySelection` in `org.chromium.web-custom-data`) marks that copy, and the hotkey treats it as no selection. The write is per-character Unicode key events; a line break goes in one event with its neighbour, since VS Code drops a lone `\n`.
- Input source switching — Text Input Sources / TISSelectInputSource.
- Settings — the auto-correct checkbox is disabled (shown off, stored preference kept, ⓘ icon with the reason `settings.autoCorrectUnavailable` naming the enabled layouts as an instant tooltip — `NSInitialToolTipDelay` = 0, app-wide) while the enabled layouts are all one script (`updateAutoAvailability`, re-run on the enabled-sources notification).
- Settings — a single window that also holds the About info (logo / version / link). Menu-bar item (`NSStatusItem`), login item (`SMAppService`), conflict check against `com.apple.symbolichotkeys`. Both live hotkeys + auto-correct are suspended only while a shortcut recorder field is actively capturing (`recordingHotkey`, set by `ShortcutField.onRecordingChanged`), so the keys being recorded can't trigger a conversion — merely having Settings open leaves the hotkey live. `finalizeSequence` commits a tap sequence and re-applies the hotkey while the field is still focused, so the gate holds the re-apply off until the recorder stops. `Cmd+W`/`Cmd+Q` handled by physical keyCode (no main menu).
- Press-again cycle: a second hotkey within `undoWindow` (1.5 s) of a conversion retypes the original into the next layout (engine `retypeAlternatives`: every other enabled layout, best-reading first, distinct results only; `Conversion.alternatives`), and once they are exhausted reverses the conversion. With two layouts the second press is the undo. Single-tap hotkeys only; auto-corrections carry no alternatives.
- Sparkle auto-update under `#if SPARKLE` (only compiled when `WITH_SPARKLE=1`). `AppController` is the `SPUUpdaterDelegate`: a silently downloaded update installs and relaunches at once (`willInstallUpdateOnQuit`), since a menu-bar app never quits.
- `dbg(_:)` writes to `/tmp/relayout.log` only under `-DDEBUG`. Release builds **must never** write selection text to disk — the empty release body is inlined away under `-O`. Don't add prints of user text outside this guard. Even the debug trace holds no typed text: `dbgRedact` masks every quoted string (letters → `a`/`я`, digits → `0`, symbols → `·`), the tap line names only non-text key codes, and nothing is written under secure input. Keep user text inside `debugDescription` quotes so the mask catches it.

`macos/tests.swift` provides a `@main` entry under `-DTESTING` that replaces the GUI bootstrap so the unit tests exercise the **real** engine + helpers, not copies.

Diagnostics without the GUI: `ReLayout.app/Contents/MacOS/ReLayout --enabled` lists the enabled input sources in order; `--selftest` prints sample conversions.

## Windows port (`windows/`, preview)

- `main.swift` — single-instance mutex, message loop (with `IsDialogMessageW` for our windows), the per-hotkey double-tap gate, the hotkey retype and press-again undo.
- `WinHotkey.swift` — low-level keyboard hook: two hotkeys (`HotkeySlot`: convert, auto-correct on/off; unset = vk 0), each a `HotkeyDetector` for combos and bare-modifier taps that posts `WM_RETYPE` / `WM_TOGGLE_AUTO`; hotkey capture for Settings; also feeds the auto mode. A key a hotkey swallows never reaches the undo window or the auto mode.
- `WinLayout.swift` — builds `LayoutMaps` via `ToUnicodeEx` (cached per HKL), language code, lists/switches HKLs.
- `WinInput.swift` — `SendInput` writes: text as real key presses of the target layout after switching to it (`typeText`; VK_PACKET can't be batched — a busy app reads one character several times, undocumented), paced Unicode events as the fallback, Backspace, Shift+Left; the Ctrl+C fallback read with clipboard save/restore, `pumpWait`, focus/console helpers.
- `WinUIA.swift` + `native/relayout_uia.cpp` — UI Automation: the selection, the field snapshot for the Enter follow-up, the password-field flag. C++ because Swift has no COM.
- `WinTheme.swift` + `native/relayout_theme.cpp` — light/dark: DWM title bar, the system's dark control styles, theme colors for background/text/separators, dark tray menu (uxtheme ordinal 135).
- `WinSpell.swift` + `native/relayout_spell.cpp` — the system spell checker (Windows Spell Checking API, `ISpellCheckerFactory`/`ISpellChecker`) for the `autoSpell` option: `isWord` / `spellGuesses` feed engine `spellCheckedTarget` / `spellRepairedTarget`, `hasSpellDictionary` decides whether Settings offers it.
- `WinUpdate.swift` + `native/relayout_http.cpp` — the update check (GitHub latest release over WinHTTP, which Swift's WinSDK module lacks).
- `WinAuto.swift` — the auto-correct mode around the engine's `AutoRun`, with a mouse hook that ends the run on a click; `setAutoMode` (checkbox and on/off hotkey) and `toggleAutoMode` (a no-op while auto-correct is unavailable, as the disabled checkbox).
- `WinTray.swift` — tray icon and menu, launch-at-login (HKCU Run), the hidden window that runs fixes off the hook. While auto-correct is on, the glyph gets a green dot in its top-right corner, drawn at runtime over the loaded ICO (`withAutoDot`: GetIconInfo/GetDIBits → pixels → CreateIconIndirect); deeper green on a light taskbar, lighter on a dark one. Re-drawn on every auto-mode change, taskbar theme change, and a layout change seen by Settings.
- `WinSettings.swift` / `WinExceptions.swift` / `WinLearned.swift` / `WinPrefs.swift` / `WinLoc.swift` / `WinTooltip.swift` — Settings, Exceptions and Learned-words windows, preferences in the registry, UI strings, the ⓘ tooltip.
- `Identity.swift` / `Version.swift` — repo slug and version, overwritten by CI before `swift build`; `WinDebug.swift` — dev-build trace log.
- `packaging/windows/relayout.iss` — Inno Setup script for the installer.

Only built when host OS is Windows (`#if os(Windows)` gate in `Package.swift`); macOS `swift test` ignores the executable target. Selection is read through UI Automation (`windows/native/relayout_uia.cpp`, in the C++ target `RelayoutNative` — Swift has no COM); the clipboard is the fallback for controls without UIA text, and is saved and restored around it. `WinAuto.swift` is the opt-in auto-correct mode: the keyboard hook feeds typed characters into a word buffer, a boundary (space/Tab) runs the shared `decideAutoTarget`, and the fix is backspaced in and retyped. Trigram models ship as `trigram/<lang>.txt` next to the exe. Short words follow the macOS neighbour rule, and the Enter follow-up (skipped in consoles, where the hotkey converts only the typed word) uses a second UIA call (field length, caret, selection, the text before the caret) with the engine's `enterOutcome`. The experimental spell-check option (`AutoCorrectSpell`, default off; Settings row under "Between similar layouts" with an ⓘ, enabled only while auto-correct is on and a system dictionary exists for an installed layout's language) runs the macOS `autoDecide` chain in `WinAuto.autoDecide`: `decideAutoTarget` → `spellCheckedTarget` → `spellRepairedTarget`, for both the boundary fix and the Enter follow-up; a repaired typo is recorded with no `autoWords`, so its undo learns no `keep`. `relayout_spell.cpp` maps a 2-letter code to a dictionary tag (the code itself if `IsSupported`, else the first `<code>-…` of `get_SupportedLanguages`), caches one `ISpellChecker` per code, and joins the UI thread's STA like the UIA reader; `reloadAutoMode` opens the dictionaries up front (`warmSpellCheckers`) so the first load does not run inside the keyboard hook's time limit. A deny-list of executables (Settings > Exceptions — a list with icons, "Exclude current app" from a foreground WinEvent hook, "Choose…") and the UIA password-field flag gate it per app and per field. UI strings come from the macOS `Localizable.strings`, shipped as `lang/<code>.lproj` next to the exe and read with the engine's `parseStrings` (`WinLoc.swift`); Settings mirrors the macOS window (logo, login + language, two click-to-record hotkey fields — convert (↺ restores Ctrl+Alt+R) and auto-correct on/off (default unset, "Not set"; ↺ clears it) — where a double tap is recorded as two taps and the other field's keys are refused with a beep, auto-correct with an ⓘ tooltip and Exceptions…, centered footer); a language change or `WM_DPICHANGED` rebuilds it. The hook runs on the main thread, so every wait in the retype path uses `pumpWait` (pumps messages), never `Sleep`. Releases: on a `v*` tag `build-windows` attaches the installer and the portable SFX (x64, arm64, unsigned) to the GitHub Release. `WinUpdate.swift` checks GitHub's latest release a minute after start and daily (WinHTTP via `relayout_http.cpp`), announces a newer one once in the tray and adds a menu item to its page; nothing is downloaded. Dev builds skip it.
